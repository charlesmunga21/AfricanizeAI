Arrays vs. Linked Lists

Arrays and linked lists solve the same problem — store a sequence of values — with opposite tradeoffs. Neither is "better"; each wins on exactly the operations the other loses on.

  • Access by index: arrays O(1), linked lists O(n) — you must walk from the head.
  • Insert/delete at a known position: arrays O(n) (shifting), linked lists O(1) (just repoint pointers), once you already have a reference to that node.
  • Memory layout: arrays are contiguous, so they're cache-friendly. Linked list nodes can be scattered anywhere in memory.
  • Extra memory: each linked list node stores a pointer in addition to its value, which arrays don't need.

Visual model: insert at the front, side by side

This is the single clearest example of the tradeoff. Insert the same value at the front of an array and a linked list holding the same data, and watch what each one actually has to do.

The array has to shift every existing element to make room at index 0. The linked list just points a new node at the old head and updates head — nothing else in the list is touched, regardless of how many nodes there are.

The reverse is true at the other end: appending to an array (with spare capacity) is O(1), while appending to a singly linked list without a tail pointer is O(n) — see Insert & Delete Operations.

When to use which

Reach for an array when you need fast random access by index and insertions mostly happen at the end. Reach for a linked list when you need frequent insertions/deletions at the front or middle of a sequence and don't need random access — implementing a queue, an undo history, or a stack, for example.
