Complexity & Common Pitfalls

Binary search's O(log n) time is what makes it worth the sorted-data requirement. Here's how big that gap actually gets, and the handful of classic bugs that quietly turn a correct-looking implementation into a wrong one.

Just how big is the gap?

Every additional element roughly doubles what linear search has to check in the worst case, while binary search only needs one more comparison. For a million elements, that's the difference between checking up to a million values and checking about twenty.

Common pitfalls

1. Running it on unsorted data

Binary search doesn't check whether the array is sorted — it just trusts the precondition. On unsorted data it silently returns wrong answers (or misses a value that's actually present) instead of erroring. This is the single most common real bug.

2. Off-by-one in the loop condition

# Wrong — misses checking the case low == high
while low < high:
    ...

# Right — low == high is a valid single-element range to check
while low <= high:
    ...

3. Forgetting to move a boundary

# Wrong — infinite loop: when arr[mid] < target, low never changes
while low <= high:
    mid = (low + high) // 2
    if arr[mid] < target:
        pass          # bug: forgot "low = mid + 1"
    else:
        high = mid - 1

If a boundary doesn't move on some branch, low and high can stop converging entirely — the loop never terminates.

4. Integer overflow in mid (C, Java, and other fixed-width-integer languages)

// Can overflow if low and high are both close to INT_MAX
int mid = (low + high) / 2;

// Safer — never adds two large numbers together
int mid = low + (high - low) / 2;

Python and JavaScript don't have this specific problem (their numbers don't silently wrap on overflow the way fixed-width integers do), but it's a real, historically significant bug — it shipped in Java's standard library binarySearch for years before being fixed.
