Where Software Meets Hardware

Strip away the buzzwords, and "IoT" (Internet of Things) is a fairly plain idea: ordinary physical objects — a soil probe, a factory arm, a pivot irrigator — get a small computer, a way to sense or act on the world, and a network connection. A widely-cited 2013 survey by Gubbi, Buyya, Marusic, and Palaniswami frames it simply: sensors and actuators "blend seamlessly with the environment," and the resulting information gets shared across platforms — devices and cloud software cooperating over a network, the same way any client and server do.

The part you already know

Almost all of embedded and IoT programming is variations on one loop: read some input, decide something, write some output. That's not a new idea — it's the same shape as a game loop, an event listener, or a request handler. What's different is what the input and output actually are: not a keystroke or an HTTP request, but a real voltage on a physical pin.

The bridge: GPIO

A GPIO (General-Purpose Input/Output) pin is the bridge. Treat it like a variable that's physically wired to a circuit: read it, and you get a real voltage from the outside world; write to it, and you change a real voltage out there. On an Arduino, digitalRead(pin) and digitalWrite(pin, HIGH) are literally get/set on that variable — the "hardware" part is just that the variable happens to be soldered to something real.

Sensors and actuators: two directions of the same idea

  • A sensor converts something physical — light, moisture, motion, temperature — into a signal your code can read. It's an input, a getter.
  • An actuator converts a signal your code writes into physical motion, heat, or light. It's an output, a setter.

Everything else in this module — a button moving a robotic arm, a soil probe reporting to the cloud, a camera triggering a spray nozzle — is this same read/decide/write pattern, just with progressively more interesting things on either end.
