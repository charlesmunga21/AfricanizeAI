Sensors & Actuators

The clearest real-world version of "a button moves a hand in a factory" is a PLC — a Programmable Logic Controller, the industrial computer that has run factory floors since the 1960s. A PLC continuously monitors sensors, executes control logic, and operates motors, valves, and other equipment in real time. It's not exotic hardware, and it's not doing anything you haven't already written in software — it's just running that logic against real inputs and outputs instead of an HTTP request.

The scan cycle: a while(true) loop for the physical world

A PLC repeats the same three-step cycle continuously, often hundreds or thousands of times per second:

  1. Read Inputs — check the current state of every connected sensor, switch, or button.
  2. Evaluate Logic — run the stored program against those inputs to decide what should happen.
  3. Update Outputs — change the state of connected actuators: motors, valves, lights, robotic arms.

Then it starts again. If you've ever written a game loop or a polling loop, this will look extremely familiar — it's the same while(true) { read(); update(); render(); } shape, just with sensors and actuators standing in for keyboard input and pixels.

Sensors: the inputs

A sensor's whole job is turning a physical quantity — light, temperature, pressure, distance, moisture — into an electrical signal, which gets converted into a number your code can read. Some are simple digital sensors (a button: pressed or not, nothing in between). Others are analog, reporting a continuous range — a soil moisture probe might report anywhere from "bone dry" to "saturated," not just two states.

Actuators: the outputs

An actuator converts an electrical signal from your code back into physical action: a motor spins, a valve opens, an LED lights up, a robotic arm extends. In the classic factory example, that arm doesn't move on its own — a PLC reads a button's state during "Read Inputs," decides to extend the arm during "Evaluate Logic," and only actually moves it during "Update Outputs."

Visual model: the scan cycle, live

Hold the virtual button down (or don't), and step through the scan cycle to see exactly when the arm actually moves.

Notice the arm never moves the instant you press the button — it only updates once the cycle reaches "Update Outputs." That one-cycle delay is real, and it's exactly the kind of timing detail that matters once you're controlling actual machinery.
