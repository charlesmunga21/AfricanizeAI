Databases: SQLite vs. Postgres

A database's entire job comes down to one tension: it has to store your data on disk, because disk is the only place that survives a restart — but disk is, as you just saw, roughly 1,000 times slower to read than RAM. If every query had to go straight to disk, every database would feel painfully slow. So every serious database — SQLite and Postgres included — is built around the same trick: keep a cache of frequently-used data in RAM, and only touch disk when it truly has to.

Two very different databases, the same underlying trick

SQLite is embedded — there's no separate database server. It's a library that runs directly inside your app's own process, and it reads and writes a single file on disk. Its cache — called the page cache — lives right there in your app's own memory, holding recently-used chunks ("pages") of that file so it doesn't have to keep re-reading disk.

Postgres is client-server — a separate, long-running server process holds the actual data, and your application connects to it (often over a network) to run queries. Postgres keeps its own cache in the server's memory, called shared_buffers, and — as PlanetScale's engineering blog explains — it also benefits from a second layer underneath: the operating system's own page cache, which keeps recently-read disk pages in RAM even after Postgres itself is done with them. That's two layers of RAM caching between a query and the disk, not just one.

A genuinely counterintuitive point from that same PlanetScale post: a Postgres server using a lot of RAM is usually a good sign, not a warning sign. High memory use there generally means the cache is doing its job — most of your data is sitting ready in RAM instead of waiting on disk. The number to actually worry about is high, sustained CPU usage — that's what tells you queries can't keep up.

Writing safely: the write-ahead log (WAL)

Reads are only half the story — a database also has to guarantee that once it tells you a write succeeded, that data is genuinely safe, even if the power dies one second later. Writing straight into the middle of a big, carefully organized data file on every single change would be slow and risky. Instead, both SQLite and Postgres use the same idea: a write-ahead log (WAL).

When you change a row, the database first appends that change to a simple, ever-growing log file — one quick, sequential write, which disks handle much faster than jumping around to update scattered pages. Only the WAL needs to be safely on disk for the write to be considered durable. Later, in the background, a checkpoint takes everything piled up in the WAL and folds it into the real, organized data file. If the power dies in between, the database just replays the WAL on restart and ends up exactly where it left off — nothing is lost, and nothing was ever slowly written twice.
