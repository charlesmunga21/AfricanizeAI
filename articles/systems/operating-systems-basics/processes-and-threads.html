Processes & Threads

When you open a program, the operating system creates a process for it — a running instance of that program, with its own private slice of memory that nothing else can see or touch. Open the same program twice, and you get two separate processes, each with its own copy of that private memory.

Threads: lighter workers inside one process

A process can also split its own work across multiple threads. Threads live inside one process and share all of that process's memory — unlike two separate processes, which are kept fully apart. Because threads share memory instead of each needing their own private copy, they're much cheaper to create and to switch between.

How much cheaper? Switching the CPU from one process to another takes roughly 5 microseconds. Switching between threads takes roughly 1 microsecond — about five times faster — because there's far less bookkeeping involved when everyone's already sharing the same memory.

Two real databases, two different choices

This isn't just theory — it's exactly why Postgres and MySQL are built differently underneath:

  • Postgres uses one process per connection. Every time an application connects, Postgres spawns a whole new OS process to handle it.
  • MySQL runs as a single process (mysqld) and instead gives each connection its own lightweight thread inside that one process.

Processes are safer and more isolated — one connection crashing is less likely to take down another — but heavier, with real memory and CPU overhead per connection. Threads are cheaper and faster to spin up, but share more risk if something goes wrong. Both approaches start to strain once connection counts climb into the thousands, which is exactly why connection poolers exist: a pooler sits between many client connections and the database, and funnels them through a small, fixed set of real connections — typically just 5 to 50 — reusing them instead of creating a new process or thread for every single client.
