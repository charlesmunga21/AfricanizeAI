Scheduling: Taking Turns on the CPU

Recall from the CPU submodule: a single CPU core can only truly run one instruction stream at a time. So how does your computer run dozens of programs "at once" on a handful of cores? It doesn't, really — it just switches between them so quickly that it feels simultaneous. That's the scheduler's job.

Fast enough turns feel like "at once"

The scheduler gives each runnable process a short slice of CPU time — often just a few milliseconds — then pauses it and lets the next one run. Round and round, dozens of times a second. No single program ever notices the gaps, because each pause is far too short for a human (or even most software) to perceive. That's the whole trick behind multitasking: not true simultaneity, just extremely fast turn-taking.

Switching isn't free

Every time the scheduler swaps one process out for another, it has to save exactly where that process was and restore the next one's state — a context switch. As you saw in the last submodule, that costs real time: roughly 5 microseconds for a full process switch, about 1 microsecond for a thread. It's tiny compared to a human blink — but if it happens constantly, on a heavily loaded server handling thousands of things at once, those microseconds genuinely add up, which is part of why database designers care so much about how many processes or threads they're juggling.
