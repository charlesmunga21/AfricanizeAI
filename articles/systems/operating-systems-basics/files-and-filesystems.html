Files & the File System

A disk, underneath, doesn't actually know what a "file" is. It's just a huge stretch of storage, divided into small fixed-size chunks called blocks. Names, folders, and the neat idea of a "file" are something the operating system builds on top — that layer is called the file system.

A file is really just an index entry

When you save a file, its data usually doesn't land in one single tidy chunk of disk — it gets scattered across whichever blocks happen to be free at the time, sometimes not even next to each other. What makes it feel like one coherent "file" is that the file system keeps its own index: a record of exactly which blocks belong to which file, and in what order. Ask for the file by name, and the file system looks it up in that index and reassembles the right blocks for you, instantly.

Notice the pattern: this is the same trick you've now seen several times in this section — DNS mapping a name to an address, a packet's pieces reassembled by sequence number, virtual memory mapping a private address to a real one, and now a filename mapping to scattered disk blocks. Keeping a small lookup table that translates a convenient name into where something really lives shows up everywhere in computing.

Where SQLite and Postgres actually live

This is exactly the layer SQLite and Postgres sit on top of. SQLite is famously "just a file" — its entire database really is one file, managed through this exact file-system machinery. Postgres keeps a whole directory of files (its "data directory"), each one holding pages of table and index data, also just ordinary files as far as the file system is concerned. Neither database needs to know or care which physical disk blocks its data ends up in — that's the file system's job, same as it is for a photo or a text file.
